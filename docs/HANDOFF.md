## 1. 项目缘起与目标

用户日常频繁使用 ChatGPT 等 AI 工具，许多提示词具有重复的任务模式，比如：

- 根据课程 PPT 整理适合复习和考试的笔记；
- 根据实验截图整理实验报告；
- 按固定语言风格修改文档、论文或项目材料；
- 复用经常出现的分析、总结和开发需求。

目前每次都需要重新输入一段类似的提示词，或者在聊天记录中手动查找。

**XuanEcho 旨在成为一个浏览器扩展：在获得用户授权的前提下，记录用户向 AI 网站实际发送的提示词，支持快速搜索、复用，并逐步根据使用习惯推荐可能需要的提示词。**

核心体验是：**尽量不要求用户提前手动整理提示词库，插件应帮助用户从日常使用中发现可复用的内容。**

项目名称中的 `Xuan` 取自“萱”，`Echo` 意为回响。中文标语拟定为“青萱沐雨时，旧语应时来。”；以本地配置和仓库最终内容为准。

## 3. 产品功能规划

### V0.1：最小可用版本（最高优先级）

**目标：在 ChatGPT 网页上完成“记录 → 保存 → 查找 → 复用”的完整闭环。**

功能要求：

1. **授权与开关**：首次使用明确告知采集范围和本地存储方式；由用户主动启用对 ChatGPT 的记录。支持一键暂停记录。
2. **提示词记录**：只记录用户实际发送的提示词，不记录 AI 的回复。至少保存原始文本、时间、来源平台以及稳定 ID。
3. **历史列表**：扩展弹窗展示记录；按最近使用时间排序；可查看完整文本。
4. **搜索**：按关键词查找历史提示词；支持中文，匹配部分文字即可。
5. **一键复用**：点击某条记录，将其**填入** ChatGPT 输入框，保留用户修改与确认发送的机会；**禁止自动发送**。
6. **删除与清空**：支持删除单条、清空全部；清空应有确认步骤。
7. **本地优先**：数据保存在浏览器本地，不上传服务器，不需要账号或云端服务。
8. **避免误记录**：空字符串、不合理的重复采集、AI 回复、未发送草稿等不应进入历史记录。

V0.1 不必引入大模型、向量数据库、账号系统或复杂推荐算法。

### V0.2：使用频率与基础推荐

1. 统计同一提示词（或经过明确标准化后的提示词）的发送次数、最近发送时间。
2. 支持“最常用”“最近使用”排序。
3. 在弹窗推荐区域展示高频与近期常用提示词。
4. 区分**真实发送次数**与**点击插入次数**，避免把“点了复用但没有发送”当作一次实际使用。
5. 可使用可解释的基础评分，例如频率与最近使用时间的加权组合，不要求训练机器学习模型。

### V0.3：智能识别重复任务

这是项目值得重点打磨的差异化功能。

例如以下内容：

- “整理计算机网络第三章笔记，重点讲清楚考点”；
- “整理计算机网络第四章笔记，重点讲清楚考点”；
- “根据数据库 PPT 生成适合考试复习的笔记”。

它们的字面内容不同，但属于相近的“课程笔记整理”任务。

规划能力：

1. 对语义或任务模式相似的提示词进行聚类、归组；
2. 识别任务类型和可变部分，辅助生成可复用模板；
3. 提供模板变量，例如 `{课程名称}`、`{章节}`、`{写作要求}`；
4. 保留原文与历史版本，自动归组不能覆盖原始记录；
5. 允许用户调整分组、合并或撤销错误聚类。

V0.3 的实现方案尚未定，可先考虑轻量规则或本地方法，再评估是否需要语义模型。任何远端模型调用都必须先获得用户明确同意，不能默认上传提示词。

### V1.0：场景感知推荐与多平台

长期方向：

- 结合使用频率、最近使用时间、当前输入片段和平台场景推荐提示词；
- 支持更多 AI 网站，如 Claude、Gemini（各平台独立适配与测试）；
- 提升召回速度、相关性、数据管理和可解释性；
- 在用户明确选择后，再评估可选的跨设备同步。

**不要在 V0.1 中提前实现 V1.0 的全部架构与功能。**

## 4. 关键交互设计

### 4.1 弹窗（Popup）建议结构

第一版优先清楚、简洁、好用：

```text
┌─────────────────────────────────┐
│ XuanEcho                  [设置] │
│                                 │
├─────────────────────────────────┤
│ [ 搜索历史提示词...          ] │
│                                 │
│ 最近使用                        │
│ ┌─────────────────────────────┐ │
│ │ 整理课程 PPT 笔记           │ │
│ │ 2026-11-17       [填入] [删]│ │
│ └─────────────────────────────┘ │
│                                 │
│ [记录：开启/暂停]  [管理历史]   │
└─────────────────────────────────┘
```

上述只是界面示意，不代表已经实现，也不强制逐像素照搬。

### 4.2 典型流程

- **采集**：用户启用记录 → 在 ChatGPT 输入并实际发送 → 识别已发送消息 → 本地存储 → 列表出现记录。
- **复用**：用户打开插件 → 搜索关键词 → 选中历史提示词 → 插入当前 ChatGPT 输入框 → 用户自行检查、修改、发送。
- **管理**：用户暂停采集、删除单条或清空数据，操作结果立即反映在界面中。

### 4.3 设计原则

- 中文界面为主，措辞直观，不堆砌功能或动画。
- 搜索、插入操作尽可能少点击。
- 不在用户未授权时读取并保存聊天内容。
- 对失败情况给予清楚提示（例如当前网页不支持插入、网站结构已更新）。

## 5. 工程架构建议（并非现成目录）

以现有 WXT + React 模板为基础，不要重新初始化仓库。

建议的逻辑模块：

| 模块 | 职责 |
|---|---|
| ChatGPT 内容脚本 | 检测用户已发送的提示词，并在授权后写入存储；处理一键填入请求 |
| Background / 消息层 | 按需要转发扩展与页面之间的消息，处理异步边界 |
| Storage | 提示词增删查改、配置、版本迁移 |
| Popup / React UI | 搜索框、历史列表、设置和操作反馈 |
| Domain / Types | 统一的数据类型、标准化和去重规则 |
| Tests | 存储、去重、检索等单元测试和关键交互测试 |

**存储选型**：V0.1 可以优先使用 `chrome.storage.local` 或 WXT 对应封装，避免无必要地引入 IndexedDB。数据量明显增大或需要复杂查询时再评估 IndexedDB。不要在两种方案之间过早重复建设。

**数据模型（建议，具体字段以实现为准）：**

```ts
type PromptRecord = {
  id: string;
  text: string;                 // 保留用户原文
  source: 'chatgpt';            // V0.1 先支持 ChatGPT
  createdAt: number;           // 首次记录时间，Unix 毫秒
  lastUsedAt: number;          // 最近实际发送时间
  sendCount: number;           // 实际发送次数（不是填入次数）
  insertCount: number;         // 插入次数，可后续添加
};

type ExtensionSettings = {
  captureEnabled: boolean;     // 首次使用默认 false，需用户启用
};
```

实现时需要先定义：相同文本是作为多条事件还是聚合成一条记录；若聚合，原始发送事件及准确时间如何保留。V0.1 可以采用简化规则，但应在代码中明确写出，防止统计口径混乱。

### 5.1 ChatGPT 页面适配注意事项

- ChatGPT 是动态网页，DOM 结构和输入组件可能变化；将 DOM 查找与事件处理封装为单独适配层。
- 不能仅根据每次 Enter 键判断“已发送”：还存在点击发送按钮、输入法组合键、多行输入、按钮禁用等情况。
- 监听方式需避免重复记录（如页面重渲染、发送按钮点击与消息列表变化同时触发）。
- **不要为实现采集而拦截敏感网络请求或依赖内部私有接口**；优先使用稳定且权限克制的页面交互方案，并准备失败回退。
- 插入文本要兼容受控输入框（React），不能只简单写 `element.textContent` 就认为成功；需要测试页面是否正确识别输入内容。
- 第一期只要求支持正常纯文本提示词；图片、附件、语音等内容的采集与复用留待后续评估。

### 5.2 权限与隐私

- 扩展只申请功能必要的权限；V0.1 尽量仅针对 ChatGPT 域名运行内容脚本。
- 首次使用默认关闭自动记录，主动授权后才开启。
- 不记录 AI 回复、密码框、敏感表单或其他无关页面数据。
- 数据本地保存，默认不向外发送；提供暂停、删除和清空。
- 在 README / 设置页清楚解释记录哪些数据、存在哪里、如何删除。
- 不将真实用户提示词、访问令牌、浏览器数据写入仓库、测试快照或调试日志。

## 8. V0.1 验收标准

以下交互项用于真实 ChatGPT 的手动验收，未勾选表示尚未完成实站核验。对应的合成页面自动化测试已通过，不能代替用户登录环境的核验：

- [ ] 扩展在 Chrome 中显示为 XuanEcho，能正常打开 Popup。
- [ ] 首次安装未授权时，不产生任何自动记录。
- [ ] 用户启用记录后，在 ChatGPT 实际发送一条纯文本消息，历史中出现正确内容。
- [ ] 仅编辑未发送的输入内容，不会产生历史记录。
- [ ] 一次发送不会因为多个事件监听而重复记账。
- [ ] AI 的回复不会被记录。

## 9. Git 与文档规范

- GitHub 仓库：`git@github.com:BICAamy/XuanEcho.git`（SSH）。
- 主分支：`main`（以本地实际为准）。
- 禁止提交：`node_modules/`、`.output/`、`.wxt/`、密钥、个人提示词数据库、测试中的敏感数据。
- 保持可读的文件划分；避免把数据存储、DOM 适配、业务逻辑和界面全部写进同一个组件。
- 关键功能要有简洁中文注释或 README 说明，重点说明“做什么、为什么这样做、怎么验证”。
- Git 提交消息建议遵循简单的 Conventional Commits，如 `feat: add local prompt history`、`fix: avoid duplicate prompt capture`。
- **注意：最初交接时远端为空属于历史信息**。本地现已确认有初始化提交；本轮未核对远端现状，推送前仍需检查分支和差异。

## 10. 给 Codex 的协作要求

1. 先检查真实代码与 Git 状态，再开始修改；不要把文档里的“计划”当成现状。
2. 遇到不确定的 WXT API、Chrome 扩展权限或 ChatGPT DOM 行为，应以当前环境和实际测试为准，不能靠猜测。
3. 尽量小步实现、逐步验证，不追求一次性完成所有版本。
4. 优先保证权限最小化、隐私、本地数据正确性与交互可靠性。
5. 不允许自动发送用户的提示词，不允许未授权采集或向第三方上传内容。
6. 重大依赖、架构改造、外部服务或付费方案，先说明必要性和替代方案。
7. 每次交付用简洁中文汇报：完成内容、验证结果、剩余问题、下一步。
